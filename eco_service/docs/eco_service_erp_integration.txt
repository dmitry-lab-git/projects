БЛОК 1: МАСТЕР-СПРАВОЧНИКИ И ДОМЕННЫЕ КАССИФИКАТОРЫ (DICTS)
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Точки сбора (yards): Пространственный реестр общин Ауровиля. Хранит 
  названия, адреса и GPS-координаты для построения логистических маршрутов 
  рикш и транспорта.
* Организации (organizations): Учет коммерческих и общественных объектов 
  (рестораны, офисы, фабрики, гестхаусы, школы), участвующих в сборе сырья.
* Домохозяйства (households): Учет жилого сектора с привязкой к точкам сбора 
  (yards) и количеством проживающих жильцов.
* Категории сырья (categories): Детальный классификатор фракций, на которые 
  сортируются отходы на сортировочном хабе.
* Типы мешков (bag_types): Базовые категории сырья, заявляемые при первичной 
  сдаче (чистое сухое, органика, смешанный мусор).
* Персонал (operators): Матрица пользователей системы (сборщики, сортировщики, 
  менеджеры, руководство) с ролями и уровнями доступа.
* Жизненный цикл (bag_event_types, bag_statuses): Стандарты и словарь этапов 
  обработки мешка (от сдачи жителем до взвешивания и сортировки).

2. ТЕХНИЧЕСКИЙ КОНТУР (СПЕЦИФИКАЦИЯ СУБД)
--------------------------------------------------------------------------------
* dicts.yards:
  - Поля: yard_id (UUID), name (VARCHAR 150), address (TEXT), 
    location (GEOMETRY, PostGIS), is_active (BOOLEAN), created_at, updated_at
  - Особенности: Первичный ключ, пространственный индекс GIST по геопозиции.
* dicts.organizations:
  - Поля: organization_id (UUID), name (VARCHAR 150), business_type (VARCHAR 50), 
    address (TEXT), is_active (BOOLEAN), created_at
  - Особенности: Первичный ключ.
* dicts.households:
  - Поля: household_id (UUID), user_id (UUID), yard_id (UUID), 
    family_size (INTEGER), created_at
  - Особенности: Первичный ключ, внешние ключи на точки сбора.
* dicts.categories:
  - Поля: category_id (UUID), code (VARCHAR 30), name (VARCHAR 100), created_at
  - Особенности: Первичный ключ, уникальный индекс по полю code.
* dicts.bag_types:
  - Поля: type_id (UUID), code (VARCHAR 30), name (VARCHAR 100), description, created_at
  - Особенности: Первичный ключ, уникальный индекс по полю code.
* dicts.operators:
  - Поля: operator_id (UUID), username (VARCHAR 50), full_name (VARCHAR 150), 
    role (VARCHAR 30), access_level (INTEGER), is_active (BOOLEAN), created_at, updated_at
  - Особенности: Первичный ключ, ограничения CHECK для ролей и уровней доступа (0–3).
* dicts.bag_event_types / dicts.bag_statuses:
  - Поля: event_type_id / status_id (UUID), code (VARCHAR 50/30), name, description, created_at
  - Особенности: Первичные ключи, уникальные индексы по кодам бизнес-логики.
* dicts.spatial_ref_sys:
  - Поля: srid (INTEGER), auth_name, auth_srid, srtext, proj4text
  - Особенности: Системная таблица пространственного расширения PostGIS.

БЛОК 2: ОПЕРАЦИОННЫЙ СЛОЙ И МАТЕРИАЛЬНЫЙ УЧЕТ (INFRASTRUCTURE)
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Реестр мешков (bags): Неизменяемый паспорт каждого отдельного мешка сырья 
  с момента его регистрации жителем на точке сбора (ярде). Фиксирует базовую 
  привязку мешка к жителю, точке сбора и заявленному типу отходов[cite: 1].
* Лог событий (bag_events): Сквозной неизменяемый журнал (Event Store), который 
  пошагово фиксирует всю историю перемещения и обработки мешка: сдачу жителем, 
  доставку на сортировочный хаб, взвешивание и окончательную сортировку по фракциям[cite: 1].
* Аналитическая витрина (view_material_resource_accounting): Автоматический 
  расчет материального баланса в реальном времени, собирающий суммарную массу 
  и количество мешков по каждой категории сырья для управленческих дашбордов[cite: 1].

2. ТЕХНИЧЕСКИЙ КОНТУР (СПЕЦИФИКАЦИЯ СУБД)
--------------------------------------------------------------------------------
* infrastructure.bags:
  - Поля: bag_id (UUID), resident_id (UUID), yard_id (UUID), type_id (UUID), 
    created_at (TIMESTAMP)
  - Особенности: Первичный ключ bag_id, внешние ключи на справочники типов 
    мешков (dicts.bag_types) и точек сбора (dicts.yards), индексы btree[cite: 1].
* infrastructure.bag_events:
  - Поля: event_id (UUID), bag_id (UUID), event_type_id (UUID), operator_id (UUID), 
    payload (JSONB), occurred_at (TIMESTAMP)
  - Особенности: Append-only Event Store, динамический контекст payload в формате 
    JSONB (хранит вес в кг, детали распределения фракций), внешние ключи, индексы[cite: 1].
* Аналитическое представление (view_material_resource_accounting):
  - Назначение: Выполнение операции Replay над логом событий для мгновенного 
    формирования витрины материального учета по кодам сырья и категориям[cite: 1].

БЛОК 3: ПРОГНОЗИРОВАНИЕ ПОТОКОВ ОТХОДОВ И ПИЛОТНАЯ МОДЕЛЬ
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Горизонт планирования: Расчетный период пилотного проекта составляет 
  2 месяца (60 дней) для 10 ключевых инфраструктурных объектов Ауровиля[cite: 1].
* Базовая расчетная единица: Плотный мешок объемом 60–80 литров или 
  эквивалентный упаковочный формат (связки картона, ящики)[cite: 1].
* Категоризация объектов пилотной группы:
  - Рестораны (например, Auroville Bakery): Ежедневный вывоз органики, 
    высокая доля пищевых отходов.
  - Офисы и магазины (PTDC, Visitors Centre Shop, Computation Group): 
    Преобладание сухого вторсырья (бумага, упаковка).
  - Фабрики и мастерские (Auroville Press, La Ferme Woodworks): Крупные 
    объемы производственного сухого вторсырья и обрезков.
  - Гестхаусы (Sadhana Forest, Quiet Healing Center): Интенсивное накопление 
    органики и смешанных бытовых отходов.
  - Школы и общественные центры (Isai Ambalam School, Botanical Garden): 
    Умеренные циклы накопления в рабочие дни.

2. ТЕХНИЧЕСКИЙ КОНТУР И МАТЕМАТИЧЕСКАЯ МОДЕЛЬ (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Суммарный объем генерации за период: 580–760 мешков (~4.8 – 6.4 тонны сырья)[cite: 1].
* Среднесуточный поток: 10–12 мешков суммарно со всех пилотных точек.
* Топология дедуктивной симуляции (Top-Down):
  - Переход от макроэкономических показателей домохозяйств и объектов 
    к дискретным событиям в логе `infrastructure.bag_events`.
  - Машинная генерация исторического потока через асинхронный сид-движок 
    на Python (с использованием Pydantic-валидации структуры payload).
  - Строгое соответствие сходимости итогового баланса по фракциям 
    (`CLEAN_DRY`, `DIRTY_MIXED`, `ORGANIC`) с точностью до грамма[cite: 1].

БЛОК 4: АВТОМАТИЗИРОВАННЫЙ СИД-ДВИЖОК И СИМУЛЯЦИЯ ПИЛОТА
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Автоматизация развертывания: Для быстрой подготовки тестовой среды и демонстрации 
  работы ERP-системы используется автономный скрипт симуляции (`environment_initializer.py`), 
  опирающийся на глобальные параметры конфигурации (`model_config.py`).
* Идемпотентность запуска: Перед стартом симуляции система производит гарантированную 
  очистку (каскадный TRUNCATE) только транзакционных логов (`infrastructure.bags` и 
  `infrastructure.bag_events`), не затрагивая статические мастер-справочники схемы `dicts`.
* Имитация реальной активности: Движок циклически воссоздает двухмесячный поток 
  жизнедеятельности Ауровиля (с 1 сентября по 31 октября 2026 года), генерируя реальные 
  сценарии сдачи отходов от рядовых домохозяйств и 10 ключевых типов инфраструктурных 
  объектов (рестораны, офисы, фабрики, гестхаусы).

2. ТЕХНИЧЕСКИЙ КОНТУР И КОНФИГУРАЦИЯ СИМУЛЯТОРА (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Глобальные параметры симуляции (`model_config.py`):
  - Временной диапазон: 2026-09-01 07:00:00 UTC по 2026-10-31 21:00:00 UTC.
  - Вероятность активности домохозяйств: 40% в сутки (`HOUSEHOLD_DAILY_ACTIVITY_PROBABILITY = 0.4`).
  - Профили отходов: Жестко заданные диапазоны веса (в кг) и весовые коэффициенты 
    для фракций (`ORGANIC`, `DIRTY_MIXED`, `CLEAN_DRY`) с привязкой к кодам категорий.
  - Профили организаций: Дифференцированные вероятности и объемы образования отходов 
    для ресторанов, офисов, фабрик и гестхаусов.
* Архитектура сид-скрипта (`environment_initializer.py`):
  - Асинхронное подключение к СУБД с использованием пула соединений (`asyncpg`).
  - Использование фиксированных системных UUIDv4 для этапов жизненного цикла 
    (`SUBMITTED`, `ARRIVED`, `WEIGHED`, `SORTED`).
  - Автоматическое распределение ролей полевого персонала (`COLLECTOR`, `SORTER`) 
    из пула активных операторов справочника `dicts.operators`.
  - Формирование динамического контекста в формате JSONB для каждого события 
    (логистика рикш/грузовиков, масса в кг, результаты распределения по фракциям).

БЛОК 5: РОЛЕВАЯ МОДЕЛЬ, БЕЗОПАСНОСТЬ И ИНТЕГРАЦИЯ С МЕССЕНДЖЕРАМИ
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Четырехуровневая матрица доступа (RBAC): Строгое разграничение прав для 
  управления службой силами малой команды и предотвращения ошибок ввода:
  - Уровень 0 (Резиденты / Менеджеры организаций): Внешний PWA / Telegram Mini App 
    для просмотра расписания, заявок на спец-вывоз и личной статистики.
  - Уровень 1 (Сборщики / Сортировщики): Полевые интерфейсы для фиксации забора 
    партий, сканирования QR-кодов и внесения веса фракций на весах хаба.
  - Уровень 2 (Менеджеры): Диспетчерский веб-кабинет для контроля маршрутов, 
    разбора инцидентов и управления справочниками.
  - Уровень 3 (CEO): Стратегический дашборд со сквозным аудитом KPI и экспортом отчетов.
* Мессенджер-агностическая архитектура: Система не привязана к конкретным брендам 
  (Telegram, WhatsApp и др.). Авторизация строится на полиморфной связке полей 
  `messenger_provider` и `messenger_uid`, что позволяет менять интерфейсы без миграций.

2. ТЕХНИЧЕСКИЙ КОНТУР И КОНТУР БЕЗОПАСНОСТИ (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Изолированная схема `security`: Физическое отделение данных безопасности 
  (пароли, сессии, ключи мессенджеров) от бизнес-логики и транзакционных логов.
* Единый субъект безопасности: Сквозной `user_id` (UUIDv4) выступает базовым 
  интентификатором, провязываемым как `operator_id` или `resident_id` в других схемах.
* Защита на уровне СУБД:
  - Нативное хэширование учетных записей по стандарту bcrypt.
  - Ограничения `CHECK` на роли (`'COLLECTOR'`, `'SORTER'`, `'MANAGER'`, `'CEO'`) 
    и числовые уровни доступа (`access_level BETWEEN 0 AND 3`)[cite: 1].
  - Immutable Audit Trail: Регистрация сессионного контекста (IP, User-Agent, 
    временная метка в UTC 0) при каждом входе через внешние интерфейсы.

БЛОК 6: ФИЗИЧЕСКАЯ МАРКИРОВКА И ПОЛЕВАЯ ЛОГИСТИКА
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Проблема полевого учета: Традиционные бумажные стикеры и маркеры быстро портятся 
  при контакте с влажной органикой, грязью и погодными условиями Ауровиля, что 
  приводит к потере идентичности мешка и сбоям в учете.
* Технологическое решение: Внедрение портативных Bluetooth-термопринтеров 
  (модели Niimbot B1 / B21), позволяющих печатать влагостойкие самоклеящиеся 
  этикетки из полиэстера (PET) или полипропилена непосредственно на точке сбора.
* Процесс полевой маркировки:
  - Сборщик при выдаче пустого мешка или приеме заполненной партии генерирует 
    уникальный QR-код через мобильное приложение (PWA / Telegram Mini App).
  - Принтер мгновенно печатает износостойкую термотрансферную метку, содержащую 
    индивидуальный идентификатор (`bag_id`), тип отходов и привязку к ячейке.
  - На сортировочной станции хаба оператор считывает метку сканером или камерой 
    смартфона, мгновенно подтягивая всю историю мешка из Event Store.

2. ТЕХНИЧЕСКИЙ КОНТУР И ИНТЕГРАЦИЯ ОБОРУДОВАНИЯ (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Параметры печати и расходных материалов:
  - Форм-фактор этикетки: Самоклеящаяся лента из полипропилена (PP) / полиэстера (PET), 
    устойчивая к разрывам, ультрафиолету, влаге и маслам.
  - Протокол связи: Bluetooth Low Energy (BLE) для прямого сопряжения мобильных 
    терминалов полевых сборщиков с принтерами Niimbot без привязки к сотовой сети.
  - Генерация полезной нагрузки (Payload): Каждый QR-код кодирует стандартный 
    URI-идентификатор или UUIDv4 мешка, соответствующий записи в таблице 
    `infrastructure.bags`.
* Интеграция с программным контуром:
  - Отправка команды печати из мобильного интерфейса через нативные JS-библиотеки 
    или Web Bluetooth API.
  - Мгновенная фиксация факта печати и выдачи в append-only логе событий 
    (`infrastructure.bag_events`) с привязкой к сессии полевого оператора.
================================================================================

БЛОК 7: АЛЬТЕРНАТИВНЫЙ ВАРИАНТ — СМАРТ-КАРТЫ И КОНТЕЙНЕРЫ С ВЕСАМИ
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Суть альтернативного подхода: Переход от персональных QR-меток к бесконтактным 
  пластиковым RFID/NFC-картам для жителей и автоматизированным умным контейнерам, 
  оснащенным встроенными весами и считывателями чипов.
* Преимущества для бизнеса:
  - Максимальная скорость сдачи сырья жителем (достаточно приложить карту к контейнеру).
  - Автоматическое определение массы отходов в момент выброса без ручного ввода.
  - Исключение человеческого фактора и ошибок при фиксации веса на весовой станции.
* Ограничения и риски:
  - Существенно более высокая стоимость капитальных затрат (CapEx) на закупку 
    оборудованного парка контейнеров, весовых датчиков и контроллеров.
  - Зависимость от стабильного энергоснабжения и беспроводной связи в точках сбора.
  - Риск утери или повреждения пластиковых карт резидентами.

2. ТЕХНИЧЕСКИЙ КОНТУР И АРХИТЕКТУРА ОБОРУДОВАНИЯ (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Идентификация пользователя: Внедрение RFID/NFC-чипов на пластиковых картах, 
  привязанных на бэкенде к учетной записи резидента (`dicts.households`).
* Интеграция «умного» оборудования на точках сбора (`yards`):
  - Аппаратные модули: Встроенные тензодатчики (весы) в конструкцию контейнера, 
    контроллеры с поддержкой IoT (например, ESP32 / Raspberry Pi Pico W) и RFID-ридеры.
  - Передача данных: Отправка телеметрии о сессии взвешивания и ID карты через 
    MQTT-протокол или сотовый модуль (GSM/GPRS/LTE-M) прямо в Event Store.
* Изменения в структуре базы данных:
  - Расширение схемы `dicts` таблицей привязки физических чипов (`rfid_cards`).
  - Добавление новых типов автоматизированных IoT-событий в `infrastructure.bag_events` 
    (фиксация сброса контейнера с мгновенным весом).

БЛОК 9: ЗАКЛЮЧЕНИЕ И ПЕРСПЕКТИВЫ РАЗВИТИЯ СИСТЕМЫ
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
* Итоги проектирования: Разработанная ERP-система «Auroville Eco-Service» представляет 
  собой целостный, модульный и масштабируемый инструмент, полностью адаптированный 
  под специфику экологических инициатив общины.
* Ключевые ценности для руководства:
  - Прозрачный материальный учет от сбора на объектах до переработки сырья на хабе.
  - Строгое разграничение ответственности персонала через четырехуровневую матрицу ролей.
  - Гибкость внедрения: от полностью бесплатного ручного учета (Zero CAPEX) 
    до использования смарт-принтеров или автоматизированных контейнеров.
* Стратегия перехода и фактор успеха: Успешное внедрение напрямую зависит от 
  взвешенных и гибких решений по выбору варианта реализации — по принципу 
  «от простого к сложному», а также от высокой вовлеченности и активного участия 
  команды ECO SERVICE и резидентов города на каждом этапе масштабирования.
* Дальнейшее развитие: После успешного завершения 2-месячного пилота и анализа 
  накопленных данных планируется тиражирование решения на все районы Ауровиля 
  и интеграция с внешними эко-платформами.

2. ТЕХНИЧЕСКИЙ КОНТУР И ИТОГОВАЯ АРХИТЕКТУРА (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Стек технологий:
  - СУБД: PostgreSQL 13+ с поддержкой пространственного расширения PostGIS.
  - Архитектура данных: Event Sourcing (append-only лог `infrastructure.bag_events` 
    и динамический JSONB-контекст), разделение на изолированные схемы (`dicts`, 
    `infrastructure`, `security`, `analytics`).
  - Инфраструктура симуляции и бэкенда: Python (asyncpg, pydantic) для генерации 
    и тестирования потоков данных.
* Архитектурная адаптивность и готовность: Модульная структура базы данных 
  и гибкие сценарии внедрения позволяют бесшовно наращивать технологическую 
  сложность без остановки основных бизнес-процессов и потери накопленных данных 
  в Event Store. Система полностью готова к развертыванию в продуктивной среде 
  и интеграции с мобильными клиентскими интерфейсами (PWA / Telegram Mini Apps).

БЛОК 10: ЭКОНОМИЧЕСКАЯ МОДЕЛЬ И ГРАДАЦИЯ СЦЕНАРИЕВ ВНЕДРЕНИЯ (CAPEX / OPEX)
================================================================================

1. УПРАВЛЕНЧЕСКИЙ КОНТУР (БИЗНЕС-ОПИСАНИЕ)
--------------------------------------------------------------------------------
Для реализации проекта «Auroville Eco-Service» разработана гибкая градация 
сценариев внедрения — от полностью бесплатного (Zero CAPEX) до высокой 
автоматизации. Это позволяет запустить пилот при любом стартовом бюджете:

* Уровень 1 (Самый бюджетный / Ручной ввод): 
  - Суть: Ввод показателей весового баланса через веб-интерфейс на хабе 
    (масса мешков на входе -> масса отсортированного ресурса по фракциям на выходе).
  - Экономика: 0 CAPEX, 0 OPEX (нужен только интернет и любой браузер).
  - Требования к персоналу: Базовая внимательность при ручном вводе чисел.

* Уровень 2 (Стационарная маркировка объектов):
  - Суть: Маркировка баков общин и организаций долговечными физическими табличками 
    (ламинированная бумага или износостойкий пластик) с уникальными текстовыми кодами.
  - Экономика: Минимальные копеечные затраты на ламинацию/печать 10-15 табличек.
  - Требования к персоналу: Обучение операторов точному текстовому вводу кодов 
    объектов с табличек в систему при заборе и взвешивании.

* Уровень 3 (QR-коды на баках и мобильное сканирование):
  - Суть: Разовая капитальная маркировка всех стационарных баков наклейками 
    с QR-кодами. Закупка 1–3 портативных термопринтеров для первичной оклейки 
    и периодического обновления выцветших/поврежденных меток.
  - Экономика: Низкий CAPEX (1–3 принтера Niimbot B1/B21 + комплект наклеек), 
    минимальный OPEX на редкую замену меток.
  - Требования к смартфонам операторов: Достаточно любого базового бюджетного 
    смартфона (Android 7.0+, камера от 8–13 Мп с автофокусом для стабильного 
    считывания QR-кодов, поддержка Bluetooth 4.2+ для связи с принтером и любой 
    современный веб-браузер).

* Уровень 4 (Индивидуальный QR-учет каждого мешка):
  - Суть: Продвинутый операционный учет с печатью влагостойкой термотрансферной 
    этикетки (PET/PP) для каждого отдельного мешка в момент сдачи/забора.
  - Экономика: Средний CAPEX (парк принтеров) и регулярный OPEX на постоянный 
    расход термоэтикеток (из расчета ~580–760 мешков на пилотный период).
  - Требования к персоналу: Минимальные (сканирование готового QR-кода за 1 секунду).

* Уровень 5 (Автоматические смарт-приемники и RFID-карты):
  - Суть: Вершина MVP. Бесконтактные пластиковые карты резидентов и автоматические 
    контейнеры с встроенными тензодатчиками и IoT-контроллерами.
  - Экономика: Высокий CAPEX (закупка весового IoT-оборудования, контроллеров, карт), 
    но предельная надежность и полное исключение человеческого фактора.

2. ТЕХНИЧЕСКИЙ КОНТУР И СТРУКТУРА ЗАТРАТ (СПЕЦИФИКАЦИЯ)
--------------------------------------------------------------------------------
* Покрытие разработок и поддержки:
  - Проектирование архитектуры СУБД, создание сервисов, интеграция и техническое 
    сопровождение на всех уровнях полностью обеспечиваются командой Dmitry Lab (0 CAPEX на IT).
* Обязательный базовый OPEX (для всех уровней):
  - Аренда VPS-сервера с PostgreSQL/PostGIS, продление доменного имени, SSL.
* Сравнительная матрица сценариев:

  Уровень 1: CAPEX = $0 | OPEX = $0 (только хостинг) | Аппараты = Нет
  Уровень 2: CAPEX = ~$5 | OPEX = $0 | Аппараты = Нет
  Уровень 3: CAPEX = ~$60-120 (1-3 принтера) | OPEX = минимальный | Аппараты = Niimbot B1 + базовый смартфон (Android 7.0+, камера с автофокусом)
  Уровень 4: CAPEX = ~$150-200 | OPEX = ~$30-50/мес (ленты) | Аппараты = Niimbot B1/B21 + смартфоны
  Уровень 5: CAPEX = $1000+ | OPEX = обслуживание IoT | Аппараты = Тензо-контейнеры + RFID-ридеры + карты
