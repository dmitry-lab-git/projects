# ACCESS & CREDENTIALS PROVISIONING MANIFESTO (DB ROLES & .ENV)

## 1. Core Security Principles
When provisioning access for any new service, worker, script, or application within the ecosystem (`Ledger`, `core`, `eco_service`, `pwa`), strictly adhere to the following rules:
1. **Principle of Least Privilege (PoLP):** Never use `postgres` or shared superuser credentials in application code. Every functional worker must have its own dedicated, isolated PostgreSQL role.
2. **Zero Secrets in Git:** All `.env` files must reside strictly inside `/home/fujitsu-u745/Projects/secure_folder/<service_domain>/` outside version-controlled directories, with `chmod 600` file permissions.
3. **Mandatory Audit Registration:** Every newly created database role must be immediately registered in `development.role_metadata` (linked via `role_oid` and `UUID`) so it is visible in `development.v_db_access_registry`.

---

## 2. Standard Naming Conventions
* **Database Role Name:** `<module_or_worker_name>_svc` or `<module_or_worker_name>_worker` (e.g., `data_ingress_worker`, `receipt_processor_svc`, `pwa_workers_inspector`).
* **Secrets Directory:** `/home/fujitsu-u745/Projects/secure_folder/<domain_name>/.env`
* **Environment Variable Prefix (Optional for multi-service `.env`):** `<SERVICE>_DB_HOST`, `<SERVICE>_DB_PORT`, `<SERVICE>_DB_NAME`, `<SERVICE>_DB_USER`, `<SERVICE>_DB_PASS` (or standard `DB_*` if the `.env` file is dedicated to a single service).

---

## 3. Execution Checklist & Templates

Whenever instructed to provision a new worker or service access, generate the following **three artifacts** in order:

### Artifact A: PostgreSQL Role & Least-Privilege Grants (SQL)
1. Create a `LOGIN` role with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`.
2. Grant `CONNECT` only to the target database (e.g., `ledger`).
3. Grant `USAGE` on required schemas and explicit table-level privileges (`SELECT`, `INSERT`, `UPDATE` — avoid `DELETE` or `TRUNCATE` unless explicitly required by retention logic).
4. Grant `USAGE, SELECT` on sequences if the role performs `INSERT` into serial/identity tables.

```sql
-- 1. Create isolated role
CREATE ROLE <role_name> WITH
    LOGIN
    PASSWORD '<STRONG_GENERATED_PASSWORD>'
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE
    NOREPLICATION;

-- 2. Database & schema access
GRANT CONNECT ON DATABASE <db_name> TO <role_name>;
GRANT USAGE ON SCHEMA <target_schemas> TO <role_name>;

-- 3. Granular table & sequence privileges
GRANT SELECT, INSERT, UPDATE ON <target_tables> TO <role_name>;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA <target_schema> TO <role_name>;
```

### Artifact B: Registry Entry in `development.role_metadata` (SQL)
Immediately link the new PostgreSQL role OID to a UUID record in the central access registry:

```sql
INSERT INTO development.role_metadata (role_oid, role_name, purpose, env_location)
SELECT 
    oid,
    rolname,
    '<Clear description of service responsibility and privilege scope>',
    'secure_folder/<domain_name>/.env'
FROM pg_roles
WHERE rolname = '<role_name>'
ON CONFLICT (role_oid) DO UPDATE SET
    role_name = EXCLUDED.role_name,
    purpose = EXCLUDED.purpose,
    env_location = EXCLUDED.env_location,
    updated_at = CURRENT_TIMESTAMP;
```

### Artifact C: Python `.env` Provisioning & Loader Snippet (WSL / Python)
For Python services, generate a WSL command to create the secure directory, write the `.env` template, lock file permissions (`600`), and verify the file is excluded from Git:

```bash
mkdir -p /home/fujitsu-u745/Projects/secure_folder/<domain_name> && \
cat << 'EOF' > /home/fujitsu-u745/Projects/secure_folder/<domain_name>/.env
# Service: <role_name>
DB_HOST=localhost
DB_PORT=5432
DB_NAME=<db_name>
DB_USER=<role_name>
DB_PASS=<STRONG_GENERATED_PASSWORD>
EOF
chmod 600 /home/fujitsu-u745/Projects/secure_folder/<domain_name>/.env
```

---

## 4. Verification Protocol
After executing Artifacts A, B, and C, always verify:
1. `SELECT * FROM development.v_db_access_registry WHERE role_name = '<role_name>';` returns the expected `role_uuid`, `granted_schemas`, and `granted_tables`.
2. The Python service connects using `python-dotenv` pointing explicitly to `PROJECTS_ROOT / "secure_folder" / "<domain_name>" / ".env"` and fails fast (`FileNotFoundError`) if the `.env` file is missing.
